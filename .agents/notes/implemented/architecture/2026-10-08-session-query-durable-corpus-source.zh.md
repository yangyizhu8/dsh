# Agent Note：session-query 语料默认改读持久日志

Status: implemented

[English](2026-10-08-session-query-durable-corpus-source.md) | 中文

## 问题

`session-query` 过去从同一进程中打开的 Session 的内存日志解析语料。`snapshotLive` 会克隆该日志的每一条事件，`sourceLive` 则在批量投影期间借用它，因此任何一次语料读取都会物化整份活日志。

该成本随会话长度增长，如今已成为长跑宿主堆内存的主要部分。2026-10-08 对一台在跑实例的画像显示：六个打开中的会话共持有 4,179,914 条事件，其中单个会话的 1,362,229 条事件（每条约 1,024 字节 JSON）占到 `heapUsed` 的约 96%。而只做折叠、分页或检索的调用方并不需要内存里的副本，同样的事件在持久层已有。

## 决定

`Config.corpusSource` 决定「本进程中打开的会话」从哪份日志读取，默认为 `durable`。

- `durable`：对活会话 id 也读持久日志；当持久层未挂载、该 id 没有持久物件、或持久读失败时，回退读活日志。因此原设计携带的韧性属性——后端不可用不会让本进程已持有的历史变得不可读——以更强的形式保留下来：语料**优先**持久日志，**并且**保留活日志回退。
- `live`：恢复直接读内存日志，包括「在持久前缀被 inspect 期间才挂上的活主体优先」这一偏好。它最多比持久日志新一个未 flush 的写入批次，因为 `append` 是尽力而为、`flush` 才是持久屏障。

该偏好作用于语料的两个入口：`load` 与 `projectMany`。在 `durable` 下，批量路径会把已知活会话 id 也送进持久读，而不再走同步活投影，因此一次批量不会物化活会话的整份日志。

## 备选方案

保留活日志优先、改为给活事件数组设上限：**因次序问题否决**——该上限要求消费方不再读取任意旧位置，而生产包中仍有 72 处同步历史读带有延期的迁移。把语料改为读持久日志不需要这个前置条件。

只读持久日志、不设活日志回退：**否决**，因为它丢掉了原设计记录的属性——后端缺席或失败会让本进程持有的历史不可读。

在活日志旁再缓存折叠后的语料值：**否决**，因为持久日志已持有同样的事件，第二份缓存只会带来自己的失效面，却省不掉这次读取。

## 影响

- `durable` 语料的答案最多落后活日志一个未 flush 的写入批次。需要最新尾部的部署可用 `corpusSource: 'live'` 读取。
- 无论持久读的结果如何，活日志始终可读：后端失败或缺席只会失去新鲜度，不会失去可读性。
- 尚未物化的活会话仍由内存提供：持久路径在列目录后即停止，不会去 inspect 缺失的物件。
- 语料不再依赖活数组的完整性，这是日后为活会话保留量设上限的前置条件。
